# 第十一轮运行时资源与生命周期审查

日期：2026-09-21。本文只记录可由当前代码和已有实测支持的结论，不把通过 Luma 启动的 Photoshop 等外部程序计入 Luma 自身运行时，也不把宿主单进程当成完整开销。

## 结论

用户目标为闲置 50–100 MB、互动 150 MB。当前 React + WPF WebView2 架构没有达到这个目标：第十轮对宿主及其所属 WebView2 进程的观测约为 595.8 MiB；第八轮隔离短测即使设置与浮岛均暂停，整棵进程树仍约 405–427 MB。暂停能停止不必要渲染并降低长期活动风险，但不会卸载 Chromium 浏览器、GPU、网络和渲染进程，不能据此声称内存达到 100/150 MB。

本轮没有发现可以用低风险参数调整把约 596 MB 降至 150 MB 的证据。设置与搜索 WebView 已按需创建、关闭时 Dispose；浮岛 WebView 为保证顶边唤出首帧和现有可见性握手而常驻，收起后折叠并调用 `TrySuspendAsync`。继续压缩需要改变窗口生命周期或 UI 技术路线。

## 本轮低风险修复

浮岛暂停期间，宿主原先仍直接调用 `PostWebMessageAsJson`。WebView2 对暂停页面没有本项目可依赖的消息排队保证，因此其他窗口保存后的 `app.stateChanged` 可能没有被浮岛应用，恢复时显示旧配置。

现在浮岛仅对 `app.stateChanged` 使用一个有界槽位：暂停期间反复保存只保留最新序列化状态；恢复 Core 后先补发最新状态，再继续本次可见性事件。响应、`window.visibility` 及其他消息不进入该槽位，避免改变 protocol=1、响应时序或形成无界队列。发送失败会把同一条最新状态放回槽位，等待下次恢复。

`WebViewReliability` 继续以 `CoreWebView2.IsSuspended` 为真源。导航会自动恢复 Core，因此不能使用本地缓存判断暂停状态；设置和搜索在最小化及导航完成后重新核对并请求暂停。三个窗口关闭时仍解除事件并 Dispose，不保留已关闭页面。

## 架构选择与成本

1. **销毁收起后的浮岛 WebView，唤出时重建。** 这可能降低长时间纯托盘场景的进程占用，但需要重做 DockWindow 工厂、路由 Attach/Detach、崩溃恢复、首帧 readiness、visibilityId 重放、双屏热区唤出等待和配置补发。每次冷启动 Chromium 页面也会增加唤出延迟。必须先做隔离原型，比较释放后的真实进程树与 P95 首次唤出时间，不能直接并入当前交互基线。
2. **用原生轻量 UI 重写常驻浮岛，只在设置页使用 WebView2。** 这是较有可能接近闲置 50–100 MB 的路线，但等同于重写浮岛渲染、动效、拖放、长按层级、命中区域与前端共享组件，属于高成本架构变更。
3. **保留 WebView2 架构并接受实测预算。** 可继续做五小时稳定性、暂停正确性和峰值保护，但应以实测建立预算，不能继续声明 100/150 MB 已达成。

## 可验收方案

- 每次候选包分别测量：仅托盘且浮岛暂停、浮岛展开静置、连续交互、设置窗口显示、设置窗口最小化。每项记录宿主及其 WebView2 后代的私有内存、工作集、句柄、CPU；DWM 是整机合成器指标，单独记录且不全部归因于 Luma。
- 通过进程路径、父子关系和 WebView2 用户数据目录识别 Luma 自身进程；外部启动的软件另列，不纳入运行时预算。
- 50–100 MB 闲置和 150 MB 互动仍作为失败线检查。超过即明确失败，不以暂停成功、低 CPU 或宿主内存较低替代。
- 若评估“销毁并重建浮岛”原型，验收同时要求配置更新不丢失、双屏首次唤出、650/600 ms 动效、崩溃后重新握手和连续十次唤出；报告内存节省与 P50/P95 唤出延迟。
- 五小时设置最小化场景尚需完整跑满；短测和单元测试均不能替代。

## 验证边界

本轮未启动第二个原生 GUI、未停止当前用户应用、未修改用户配置。源码宿主构建通过；并行实现合并后重跑原生单元测试，445/445 通过。该结果验证有界状态合并和原生服务逻辑，不等于真实 WebView2 内存目标或五小时稳定性验收。
