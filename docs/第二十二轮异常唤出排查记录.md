Windows允许在鼠标没有移动时因窗口变化而生成WM_MOUSEMOVE，见[Microsoft鼠标移动说明](https://learn.microsoft.com/en-us/windows/win32/learnwin32/mouse-movement)。这是排查方向，不是本次根因结论。

## 本轮改动

只增加事件诊断与唤出来源标签，保持现有激活策略和前端行为：

- 在原生进入消息中记录消息内坐标、GetCursorPos/GetPhysicalCursorPos、指针显示标志、输入来源、输入/消息时间差、命中窗口类、实际热区矩形和线程DPI上下文。
- 驻留结束记录**用于原判定的同一份坐标、HWND、按键值和放行结果**，再附诊断快照；后取的快照不冒充判定时数据。
- 区分悬停、热区单击、OLE、托盘、实例信号、设置预览、快捷键、显示变化恢复及回收反转来源。
- 不增加常驻轮询、输入钩子、网络上传或窗口标题记录，不恢复长测、自动跟进。
- 输入来源与最后输入时间仅作为证据，不能单独认定物理鼠标操作；[微软来源说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ne-winuser-input_message_origin_id)及[时间戳说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getlastinputinfo)均有边界。

另修复测试前台保护脚本兼容性：Windows PowerShell 5.1无Environment.TickCount64，旧读取会把最近输入误算成约49天前。改用32位TickCount回绕运算，未来时间戳按活跃处理。实际复验正确阻止在用户操作Illustrator时运行抢前台的检查。此脚本问题不等于Luma异常唤出的原因。

## 11:27:20新证据与0.4.5修正

诊断版现用程序在11:27:20.303记录一次进入：系统逻辑/物理坐标均为(2196,0)，输入来源2/1；11:27:20.495驻留放行时，判定使用的坐标与物理快照均为(1995,2)，期望/实际主屏热区均为x1452–2388、y0–6，最后输入距此15ms，唤出来源hover-dwell。用户明确确认**这次也是误弹**，不能将它作为用户主动操作或正常验收通过。

证据证明程序从系统读到的位置在热区内，并在首末位置变化约201px后放行；它不能证明用户本人移动了鼠标，输入来源中的hardware也可能包含具有UIAccess权限的软件注入。也没有每一步轨迹，不能精确重放这个事件或断定最后输入就是鼠标移动。

查明一个可复现的宽松条件：旧计时从首次进入开始，此后即使持续扫过整条热区也不重置，只在180ms到期时检查是否仍在范围内。因此移动中的横向经过也可能被当成悬停。0.4.5只针对这个条件修正：

- 真正的悬停要求在一个物理锚点附近停稳180ms，各轴允许3px抖动；累计漂移超出锚点容差重新计时。
- 在热区内的后续WM_MOUSEMOVE事件也更新计时；到期再采样实际位置，防止新位置已改变、对应消息尚未处理时误放行。
- 离开、重排、暂停清空旧计时；没有新增常驻轮询或全局输入钩子。
- 热区单击、OLE拖入、显式唤出和已展开浮岛的回收反转保持独立规则。
