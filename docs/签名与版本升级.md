# 签名、版本升级与回退

## 当前状态

当前发布渠道是 GitHub 私有仓库 Releases。未配置发行主体的受信任代码签名证书；产物必须标注“未签名测试版”，不能承诺消除 SmartScreen 提示。SHA256 仅验证文件一致性，不替代发布者签名。不得把自签名根证书导入用户机器绕过信任检查。

## 发行签名流程

1. 发行者向受信任 CA 或受信任签名服务完成身份验证，将可用代码签名身份接入 Windows 证书存储/签名硬件。私钥与口令不进入项目、日志或聊天。
2. `scripts/sign-artifact.ps1 -Path <Luma.exe>,<Luma.dll> -CertificateThumbprint <公开指纹>` 使用当前用户证书、SHA256 和 RFC3161 时间戳，并执行 Authenticode 验证。没有有效证书/时间戳则失败。
3. 发布脚本的 `-RequireSignature` 模式在压缩前签名宿主；安装器在生成后签名，随后生成最终 SHA256。全部集成验证必须对最终签名产物执行。第三方 Microsoft 文件保留原签名。
4. 当前没有证书，以上接入流程和拒绝无证书的检查可验证，但真正签名操作尚不能验收。不得把此项标记为已完成签名。

依据：[Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool)、[时间戳说明](https://learn.microsoft.com/en-us/windows/win32/seccrypto/time-stamping-authenticode-signatures)。

## 升级与回退

- 安装版：下载最新安装 EXE，在原目录覆盖升级；安装器优雅退出同一路径旧进程，保留配置和开机启动选择。桌面/开始菜单入口指向新版本。
- 便携版：退出托盘中的旧版本，完整解压新版 ZIP 至新目录，再启动新版本。不要只替换 EXE；移动目录后在“启动与桌面”重新创建快捷方式并按需重新登记自启动。
- 两版配置仍在 `%LOCALAPPDATA%/Luma`，升级前可在“设置与备份”导出 JSON。配置版本不变时可重新运行上一版本；未来 schema 升级必须先备份并提供迁移/回退计划。
- 发布版本必须在前端 package.json、原生 csproj、manifest、包名与 build-info.json 一致。发布资产只新增，不覆盖历史版本。
- 自动下载/静默安装暂不启用：私有仓库需要鉴权，客户端不能内置 GitHub Token；受信任自动更新还需签名及防降级校验。当前采用用户启动的完整安装包升级，防止未验证载荷替换程序。

## 正式版门槛

通过干净目标 Windows 的安装/运行矩阵、长期资源测试、输入/显卡场景检查，以及受信任签名验收，才可升级为正式稳定版；当前机器的通过结果不扩展为其他机器已通过。
