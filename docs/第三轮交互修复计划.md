# 第三轮：回收过渡、拖放与堆叠说明

依据用户本轮反馈，保留当前视觉和 protocol=1，不重写前端。

1. 原生热区接入 Windows OLE 文件拖放；拖拽和按键操作中不能被自动隐藏中断。双屏均适用。
2. 回收采用两阶段：原生发 visibility=false 请求，前端保留 DOM 完成短退出过渡，最后 sync expanded=false；原生收到完成报告后才隐藏 HWND。重新进入可以反向展开。原生有有界故障兜底。
3. `window.sync` 最小兼容补充可选 `interacting:boolean`（缺省 false）：用于拖放、按压、键盘导航、堆叠展开和导入请求中的保持展开。不得以命中矩形数量推断操作状态。expanded 在退出动画结束前保持 true。
4. 设置页支持外部文件拖到空白新建、拖到现有卡片加入堆叠；编辑弹窗支持批量拖入目录/软件/文件。说明一个图标是逻辑分组，支持 5 个目录，实际上限 200 入口；不移动文件。
5. 缩略图为用户可选建议，本轮保留现有水晶图标，不新增扫描文件夹的后台任务。优先确保拖放和自动隐藏可靠。
6. 验证：前端退出/re-entry/interaction/drop 回归；原生生命周期和拖放边缘行为；构建发布包并进行实际宿主回归，明确鼠标消息模拟和真实 OLE 的边界。

## 复核后的最小协议补充

复核发现旧退出动画的 expanded=true 与 collapsed=false 都可能在 WebView 消息队列中排队；单凭 AwaitingExpanded 无法区分新旧展开，旧 true 会错误确认新唤出，随后旧 false 再次隐藏。为精确区分，`window.visibility.data.visibilityId?: number` 与 `window.sync.params.visibilityId?: number` 增补非负安全整数编号。宿主每次可见性请求递增，前端原样回传，原生在任何区域/交互/状态变更前拒绝旧编号。字段可选兼容旧客户端，但本版原生与前端始终发送/回传。protocol=1、已有字段与方法不变。
